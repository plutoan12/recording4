# 기술 선택과 결정 기록

## 2026-09-21: 숏폼 편집에 멀티 컷·무음 빼기·배속/페이드/배경음악·미리보기

| 구분 | 내용 |
|---|---|
| 채택 | `EditSpec.segments`로 여러 구간을 이어 붙입니다. 비어 있으면 예전과 같은 한 구간이고, **FFmpeg 명령도 예전 그대로** 나갑니다(결과가 달라지지 않게). 길이 상한 180초는 원본 구간이 아니라 **이어 붙인 결과**에 겁니다. |
| 채택 | 무음 빼기는 auto-editor(퍼블릭 도메인)의 `mutMargin`·`smoothing`을 옮겨 씁니다(`pipeline.cuts`). 발화 판정은 **VAD**가 합니다. auto-editor·jumpcutter의 소리 크기 임계값 방식은 이 저장소가 실제 녹음에서 이미 실패를 쟀기 때문에 쓰지 않았습니다. |
| 채택 | 무음 빼기와 미리보기는 **제안**입니다. 얼굴·하이라이트 제안과 같은 방식으로, 자동으로 영상을 자르지 않고 사람이 편집기에서 적용합니다. |
| 채택 | 배경음악은 검사 통과한 다른 원본의 소리를 씁니다. 업로드 경로를 새로 만들지 않기 위해서입니다(대신 음악만 있는 파일은 업로드 확장자 제한에 걸립니다 — 아는 한계). `amix=normalize=0`으로 섞고, `music_duck`이면 `sidechaincompress`로 말할 때만 낮춥니다. |
| 채택 | 미리보기는 렌더와 같은 `EditSpec`을 받아 한 프레임만 뽑습니다. 설정이 갈라져 "미리본 것과 다른 결과"가 나오는 것을 구조로 막습니다. |
| 실측 | 실제 FFmpeg로 확인했습니다: 12초 원본에서 2초 + 4초(2배속) → 결과 4.0초, 소리 트랙 유지. 2초짜리 음악을 6초 결과에 되풀이해 깔기. 소리 없는 원본도 멈추지 않음. 미리보기 PNG 1080×1920. |
| 미확인 | 여백 0.2초·최소 잘림 0.5초·최소 남김 0.4초와 배경음악 -18dB는 **잰 값이 아니라 정한 값입니다.** 실제 영상과 사람 청취로 다시 맞춰야 합니다. 배속을 건 목소리의 품질도 듣고 판단해야 합니다. |

## 2026-09-21: 자막 검수를 GitHub 저장소의 브랜치·PR로

| 구분 | 내용 |
|---|---|
| 채택 | 작업 하나에 검수 브랜치 하나(`subtitle-review/<job-id>`). 자막은 `subtitles/<job-id>/<lang>.srt`, 용어집은 `glossary/<source>-<target>.tsv`로 올리고 PR을 엽니다. 다시 내보내도 같은 브랜치·같은 PR을 쓰고, **내용이 같으면 커밋하지 않습니다.** |
| 채택 | **기본 브랜치에 쓰지 않고 병합하지 않습니다.** 토큰에 병합 기능을 쓰는 코드가 아예 없습니다. 병합은 사람이 GitHub에서 합니다. |
| 채택 | 돌아온 파일은 남이 고친 글이라 그대로 믿지 않습니다. 자막 **개수**가 다르면 작업에 넣을 수 없고(어느 줄이 어느 줄인지 모름), **시각**이 바뀌었으면 문제로 보고합니다. 크기·개수·인코딩 상한을 읽기 전에 겁니다. 판정은 `pipeline.review.compare`, 규칙 안내는 PR 본문에 적습니다. |
| 채택 | 가져온 번역을 작업에 **자동으로 넣지 않습니다.** 검수 행(`subtitle_reviews.result`)에만 두고, 사람이 화면에서 문제를 본 뒤 기존 `translated_cues` 경로로 새 버전을 만듭니다. 용어집도 마찬가지로 사람이 새 버전으로 저장합니다. |
| 정정 | `media.highlights`를 보내는 `worker.highlight_tasks`가 celery `imports`에 없었습니다. 워커가 그 모듈을 들이지 않으면 셀러리가 모르는 이름이라며 버리므로 **하이라이트 추천은 운영에서 한 번도 돌 수 없었습니다.** 넣고, 디스패처의 모든 주제가 워커가 들이는 모듈을 가리키는지 보는 시험을 두었습니다. |
| 미확인 | 실제 GitHub 저장소에 올려 보지 않았습니다. 토큰 권한·PR 화면·번역가 왕복은 재지 않았습니다. 포크에서 온 PR은 읽지 않습니다(우리 저장소의 브랜치만 봅니다). |

## 2026-09-21: 번역 경로를 STT → 기계 번역 → 용어집 → LLM 보정 → QA → SRT → TTS로

| 구분 | 내용 |
|---|---|
| 채택 | 언어 목록·번역 방향은 `pipeline.languages` 한 곳. 핵심 ko·en·ja·zh 상호 12방향, ko → es·id·th·pt·vi·hi. 판정은 (source, target) 쌍이라 `EXTRA_SOURCES`에 언어를 더하면 그 언어의 방향이 열립니다. API·워커·화면이 전부 이 모듈을 봅니다. |
| 채택 | 기계 번역 공급자를 설정으로 고릅니다(`R4_TRANSLATION_PROVIDER`: google · deepl · huggingface). Google 경로는 그대로이고 DeepL은 HTTP 직접 호출, Hugging Face는 로컬 NLLB-200(유료 예약 없음). |
| 채택 | 용어집은 기존 `glossaries` 표. 기계 번역에는 용어·숫자를 자리표시자로 가려 보내고 되돌립니다(`pipeline.glossary`). LLM 보정에는 이 묶음에 나오는 용어만 규칙으로 줍니다. 새 버전을 올리면 번역 기억이 무효화됩니다. |
| 채택 | 번역 기억(`translation_memory`). 키는 출발·목표·{공급자, 모델, 용어집 버전, 보정 모델·프롬프트 버전}. 묶음 안 중복도 한 번만 보내고, 비용 추정은 기억에 없는 글자만 셉니다. 초안과 보정본을 따로 기억해 보정이 실패해도 기계 번역을 다시 사지 않습니다. |
| 채택 | 묶음은 장면 경계로 나눕니다(LLM-Subtrans SubtitleBatcher 이식, MIT). 30초 침묵에서 끊고, 100줄(DeepL 50줄)을 넘으면 가장 긴 틈에서 가릅니다. 단계 `translate:N`은 그대로라 실패한 묶음만 다시 돕니다. |
| 채택 | Claude 문맥·말투 보정은 선택(`R4_TRANSLATION_REFINE_ENABLED`, 단가 필수). 앞뒤 문맥 3줄과 초안을 함께 보내고 번호로 답받습니다. 줄 수가 틀리면 한 번 더 묻고 그래도 틀리면 실패입니다. |
| 채택 | QA는 읽기 전용(`pipeline.translation_qa`). 용어집 위반·숫자 누락·미번역·빈 줄·출발 언어 글자 잔류·목표 언어 자막 규칙(lines/cps, 시간은 원문 것)을 `translation_qa`로 남기고 화면에 보여 줍니다. 자동으로 고치지 않습니다. 같은 조각으로 `scripts/translate_pipeline.py`가 파일 하나를 끝까지 돌립니다. |
| 미확인 | 실제 DeepL·NLLB·Claude 보정 호출은 하지 않았습니다(지시: 유료 호출 금지). DeepL의 th·vi·hi 지원 여부, NLLB 품질·속도, 보정이 CER/chrF를 얼마나 바꾸는지는 잰 값이 없습니다. |
| 참고 | 코드 출처와 라이선스는 THIRD_PARTY_NOTICES.md. llm-subs(GPL)는 구조만 따랐습니다. |

## 공식 근거와 제약

- [GitHub Actions 실행 제한](https://docs.github.com/en/enterprise-cloud%40latest/actions/reference/limits): GitHub 호스팅 러너는 작업당 6시간 제한이 있습니다. 영상 작업 상태를 Actions 실행에 종속시키지 않습니다.
- [S3 서명 URL](https://docs.aws.amazon.com/AmazonS3/latest/userguide/PresignedUrlUploadObject.html): 브라우저가 AWS 자격증명을 보유하지 않고 직접 업로드할 수 있습니다. 같은 키를 덮어쓸 수 있으므로 고유한 파일 키와 업로드 완료 검증을 사용합니다.
- [S3 분할 업로드](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html): 큰 원본을 부분 단위로 전송합니다. 미완료 업로드 정리 정책도 설정합니다.
- [Celery 설정](https://docs.celeryq.dev/en/main/userguide/configuration.html): 재전달 가능성을 고려해 같은 작업을 여러 번 실행해도 문제가 없도록 구현합니다. Redis의 visibility timeout은 작업 길이에 맞춰 검토합니다.
- [Google STT V2](https://docs.cloud.google.com/speech-to-text/docs/reference/rest/v2/projects.locations.recognizers): 단어별 시간·화자 설정이 있습니다. 모든 모델·언어가 같은 옵션을 지원한다고 가정하지 않습니다.
- [Cloud Translation](https://docs.cloud.google.com/translate/docs/api-overview): Advanced의 용어집을 활용합니다. 번역 품질과 더빙 길이 적합성은 별도 평가 대상입니다.
- [ElevenLabs 타이밍 응답](https://elevenlabs.io/docs/api-reference/text-to-speech/convert-with-timestamps): 음성과 문자 타이밍을 받아 문장 타이밍·자막으로 변환합니다. 원본 구간 길이에 자동으로 맞춰진다는 의미는 아닙니다.
- [Sync 문서](https://sync.so/docs/introduction): 립싱크 후보입니다. 다중 화자, 얼굴 가림, 빠른 장면 전환 등 대표 입력으로 적용 가능성을 확인합니다.
- [YouTube 영상 리소스](https://developers.google.com/youtube/v3/docs/videos): 예약 공개는 비공개이고 아직 공개된 적 없는 영상에 설정합니다. 2020-07-28 이후 생성된 미검증 API 프로젝트의 업로드는 비공개로 제한되며 제한 해제에 감사가 필요할 수 있습니다. 계정 준비 단계에서 확인합니다.
- [YouTube 이어 올리기](https://developers.google.com/youtube/v3/guides/using_resumable_upload_protocol): 세션 URL과 전송 상태를 보존해 중단 후 재개합니다. 성공 응답을 잃었을 때도 기존 세션부터 확인합니다.
- [YouTube 쿼터 계산기](https://developers.google.com/youtube/v3/determine_quota_cost), [쿼터와 감사](https://developers.google.com/youtube/v3/guides/quota_and_compliance_audits): 업로드는 비용이 큰 호출이며 업로드·검색을 별도 쿼터로 분리하는 변경이 안내되어 있습니다. 하루 업로드 가능 편수가 처리량 상한이 될 수 있습니다. **2026-09-18 검토 시점에 이 두 페이지는 작업 환경의 네트워크 정책으로 직접 열지 못했습니다. 수치를 이 문서에 옮기지 않았으므로 계정 준비 단계에서 현재 쿼터와 상향 신청 절차를 직접 확인합니다.**
- [YouTube 영상 수정](https://developers.google.com/youtube/v3/docs/videos/update): 제목·설명·공개 상태는 수정할 수 있습니다. 업로드된 영상의 파일 교체는 지원되지 않는 것으로 보고 설계했습니다. 계정 준비 단계에서 수정 가능한 범위를 확인합니다.

## 숏폼 편집 기술 추가

수동 타임라인·대본 구간 편집 UI, FFmpeg 세로 크롭/패딩·자막 합성, 텍스트 LLM 기반 하이라이트 추천을 추가합니다. 추천 LLM 공급자는 미정이며 추천 실패가 수동 편집을 막지 않도록 분리합니다. 얼굴 위치로 좌우 중심을 **제안**하는 것까지 했습니다(적용은 사람이 누릅니다). 시간에 따라 움직이는 자르기와 다중 구간 조합은 후속 확장입니다. [상세 설계 및 공식 근거](SHORT_FORM_EDITING.md)를 참고합니다.

- 별도 오케스트레이션 서비스를 추가하지 않고 기존 PostgreSQL outbox+Celery를 사용한다. 메시지 하나당 한 단계를 실행하고 결과·후속 요청을 함께 저장한다.
- 번역과 TTS는 공급자 제한에 맞춰 배치/문장별 체크포인트를 저장한다. 립싱크는 원격 ID, YouTube는 업로드 세션과 영상 ID를 재사용한다.
- 공급자 응답 유실은 무조건 재시도하지 않고 정산 확인으로 전환한다. 비용은 실제 청구액이 아닌 설정된 보수적 상한으로 기록한다. 작업·월 예산을 함께 예약한다.
- 더빙은 FFmpeg로 타임라인에 배치한다. 기본값은 원래 오디오를 통째로 바꾸므로 배경음도 사라진다. `R4_BACKGROUND_AUDIO_ENABLED`를 켜면 목소리만 뺀 소리를 `R4_BACKGROUND_GAIN_DB`(기본 -9dB)만큼 줄여 대사 아래에 깐다. `amix`는 `normalize=0`으로 쓴다. 켜 두면 입력 수만큼 음량을 나눠 대사가 절반이 된다. 다음 문장 시작 전 여유 구간과 최대 1.15배 속도 조정만 허용한다. 더 긴 문장은 새 번역 버전으로 수정한다.
- 구체적인 실행 설정·복구·검증 한계는 [단계별 연결](CONNECTED_WORKFLOW.md)에 기록한다.


## Claude 리뷰 반영 (2026-09-18)

- DB 날짜는 SQLite의 naive 값을 UTC로 해석하고, PostgreSQL aware 값은 오프셋을 보존하여 UTC로 변환한다. 예약·실행 점유 검사에 공통 헬퍼를 사용한다.
- 공급자가 확정한 립싱크 종료 실패는 폴링 장애와 분리한다. 종료 실패는 정산 확인 후 새 시도, 폴링 장애는 기존 ID 재조회로 처리한다.
- 수정 번역의 변경되지 않은 음성은 명시적 부모 작업 선택으로 재사용한다. 모델/음성 버전을 모르는 공급자의 자동 전역 캐시는 금지하고, 명시된 버전이 있을 때만 자동 캐시를 허용한다. 문장별 입력 해시에는 모델·음성·언어·출력 계약을 포함한다.
- 실제 청구 비용은 아직 수집하지 않으므로 null로 기록하고 상한 장부와 구분한다. 오래된 미확인 예약은 알림·정산 대상으로 유지하며 자동 해제하지 않는다.


## 2026-09-18: YouTube 링크 원본 가져오기

공개 단일 영상 URL을 정규화해 yt-dlp 전용 워커에 전달한다. 범용 URL 다운로더 대신 YouTube 호스트와 영상 ID만 허용해 임의 내부 주소 입력을 차단한다. 큐/outbox와 기존 SourceAsset 상태를 재사용하며 API 프로세스에서 파일을 다운로드하지 않는다. 워커의 별도 프로세스에 환경 비밀을 전달하지 않고 파일 크기 OS 상한과 실행 제한을 적용한다. 임의 추출기·재생목록·로그인 쿠키를 사용하지 않으며 실패 시 수동 파일 등록으로 대체한다.


## 자막 표시 규칙의 기준 (2026-09-18)

- 자막 길이 단위를 글자 개수에서 **글자 폭**으로 바꾼다. 한글·한자·가나는 1자, 라틴 문자·숫자·공백·문장부호는 0.5자다. Netflix 한국어 자막 지침의 계산 방식이며 `unicodedata.east_asian_width`로 판정한다.
- 기본값을 그 지침(성인물)에 맞춘다. 줄당 16자, 2줄, 초당 14자, 최대 7초. 최소 표시 시간만 지침의 5/6초 대신 1초로 더 보수적으로 둔다.
- 이전 기본값(20자·20 CPS)은 근거 없는 제안값이었다. 특히 읽기 속도 20자/초는 한국어 기준으로 통과시켜서는 안 될 자막을 통과시킨다.
- 지침은 OTT 번역 자막용이고 숏폼은 화면·글꼴이 다르다. 최적값으로 보지 않으며 다섯 값 모두 설정으로 노출한다. 실제 화면 측정 후 조정한다.
- 지침의 구·절 단위 줄 나눔은 반영하지 않는다. 한국어 절 경계 판정은 휴리스틱 위험이 커서 한계로 남기고, 문장 → 어절 → 글자 순서를 유지한다.
- 자막 싱크 보정(ffsubsync)과 별도 VAD 패키지는 추가하지 않는다. 전자는 쓸 자리가 없고, 후자는 faster-whisper가 내장한 Silero VAD를 이미 쓰고 있다.


## 화자 분리 연결과 검증 방식 (2026-09-18)

- 읽기 속도 기본값은 12자/초다. 지침 I부(일반 번역 자막)의 한도이며, 14자/초는 II부(SDH)에서만 허용하는 상향값이라 쓰지 않는다.
- 화자 분리는 WhisperX(pyannote)로 한다. 게이트 모델이라 `R4_HF_TOKEN`이 없으면 모델을 내려받기 전에 막는다. 토큰이 없는 설치에서도 나머지 기능은 그대로 동작한다.
- 화자 분리는 대본을 고치지 않는다. 최신 버전의 글자를 그대로 두고 화자만 붙인 **새 대본 버전**을 만든다. 기존 버전은 감사용으로 남는다.
- 자막에 겹치는 화자 구간이 없으면 화자를 비워 둔다. 가까운 화자를 추측해 붙이지 않는다.
- 화자 → 음성 연결은 자동화하지 않는다. 어떤 목소리를 쓸지는 사람이 고르고 `voice_assignments`에 버전으로 쌓는다.
- 기본값과 정렬 품질은 문서로 주장하지 않고 CI에서 잰다. 자막 줄 길이는 워커 이미지 안에서 libass로 그려 픽셀로 재고, 정렬은 문장 시각을 아는 합성 음성으로 오차를 잰다. 정렬 검증은 모델을 내려받으므로 라벨·커밋 표시가 있을 때만 돌린다.


## 자막 파일(SRT·VTT) 내보내기 (2026-09-19)

- 내보내기 단위는 **클립 편집본**이다. 원본 대본이 아니라 그 편집본이 담은 자막을 내보낸다. 자막 시각은 클립 시작을 0초로 두므로 완성된 숏폼 영상에 그대로 얹힌다.
- 형식은 SRT와 WebVTT만 둔다. ASS는 영상에 굽는 용도로 이미 만들고 있고, 파일로 주면 글꼴·여백이 우리 렌더 설정에 묶여 다른 재생기에서 다르게 보인다.
- 새 의존성을 넣지 않는다. 이미 쓰는 pysubs2가 두 형식을 모두 쓴다. `srt`·`webvtt-py`는 중복이다.
- 파일을 저장하지 않고 요청할 때 만든다. 저장하면 승인·체크섬 대상인 결과물이 하나 더 생기고, 편집본과 어긋난 사본이 남을 수 있다. 계산은 대본 길이에 비례하는 문자열 처리뿐이다.
- 자막의 출처는 **렌더 요청에 저장된 설정 사본**이다. 대본은 그 뒤로 새 버전이 쌓이므로 최신 대본을 읽으면 영상과 다른 자막을 내보내게 된다.
- 화면 제목은 넣지 않는다. 제목은 화면 구성이고 SRT·WebVTT에는 위치 지정이 없어, 넣으면 클립 내내 첫 자막과 시간이 겹친다.
- 줄바꿈·분할은 영상과 같은 `apply_rules()`를 거치고, **그 편집본을 렌더할 때 쓴 규칙**으로 계산한다. 렌더가 규칙을 `MediaTask.result.subtitle_rules`에 남기기 때문이다. 표시 규칙(`R4_SUBTITLE_*`)을 렌더 뒤에 바꿔도 파일 자막은 화면 자막과 같다. 기록이 없는 옛 편집본만 지금 설정을 쓰고, 응답 헤더 `X-Subtitle-Rules: settings`로 그렇다고 알린다.


## 번역·더빙 작업 자막 내보내기 (2026-09-19)

- 자막 파일 경로를 두 곳으로 둔다. 숏폼 편집본은 `/clips/{id}/subtitles`, 번역·더빙 작업은 `/jobs/{id}/subtitles`다. 자막을 만드는 주체가 다르기 때문이다. 편집본은 사람이 편집기에서 넣은 자막이고, 작업은 번역·더빙 단계가 만든 자막이다.
- 어느 자막이 구워졌는지 정하는 순서(`aligned` → `translated` → `cues`)를 `pipeline/workflow.py:rendered_cues()` 한곳에 둔다. 렌더와 내보내기가 같은 함수를 쓴다. 두 곳에 같은 순서를 적어 두면 한쪽만 고쳐져 파일 자막이 화면 자막과 달라진다.
- 키가 있으면 빈 목록도 그 값을 쓴다. 렌더가 그 값으로 자막 없는 영상을 만들었다면 내보내기도 같은 결과여야 한다.
- 출력 창은 `0`부터 `duration`까지다. 작업 자막의 시각은 이미 출력 영상 기준이며, 구간 작업은 대본 단계에서 이미 옮겨 놓는다(`clip_cues`). 렌더가 쓰는 창과 같다.
- 자막 파일 이름에 언어를 넣는다(`job-{id}.ko.srt`). 재생기와 YouTube가 이 관례를 쓴다. 번역 단계를 지난 자막은 목표 언어이고, 번역 전 자막은 원본 언어인데 자동 감지에 맡겼으면 알 수 없으므로 그때는 언어를 빼고 이름을 만든다. 추측해 붙이지 않는다.
- 렌더를 기다리지 않는다. 대본 단계가 끝나면 그 시점의 자막을 내려받을 수 있다. 번역 검수를 파일로 하려면 더빙·렌더가 끝날 때까지 기다릴 이유가 없다.
- 표시 규칙을 만드는 함수를 `adminapi/subtitle_rules.py`로 옮긴다. 두 라우터가 같은 규칙을 써야 하고, 라우터가 다른 라우터를 불러오게 두지 않는다.
- 표시 규칙은 **렌더가 쓴 언어 규칙**으로 계산한다. 언어마다 줄 길이·읽기 속도 지침이 달라(`pipeline/subtitles.py:rules_for()`) 다른 규칙으로 계산하면 같은 자막이 다른 줄로 나온다. 렌더 단계와 내보내기가 같은 `rendered_language()` 값을 `rules_for`에 넘긴다.
- 작업도 **렌더가 그때 쓴 규칙**을 `Job.workflow_data.subtitle_rules`에 남기고 내보내기가 그것으로 계산한다. 편집본(`MediaTask.result.subtitle_rules`)과 같은 방식이고, 되살리는 함수(`adminapi/subtitle_rules.py:rules_from_record()`)도 같다. 기록이 없으면(아직 렌더하지 않은 작업) 지금 설정을 쓰고 `X-Subtitle-Rules: settings`로 알린다. 렌더 전에도 자막을 받을 수 있게 두되, 그 파일이 무엇으로 만들어졌는지는 숨기지 않는다.


## YouTube 자막 트랙 업로드 (2026-09-19)

- 기본값은 **꺼짐**(`R4_YOUTUBE_CAPTIONS_ENABLED`)이다. 영상에는 자막이 이미 구워져 있어, 트랙까지 올리면 시청자가 자막을 켰을 때 두 벌이 보인다. 켤지 말지는 사람이 결과를 보고 정할 일이라 기본으로 바꾸지 않는다.
- 올리는 자막은 **내려받기와 같은 함수**(`adminapi/artifact_subtitles.py`)가 만든다. 게시용으로 따로 만들면 영상·파일·트랙이 세 갈래로 갈라진다.
- **같은 언어 트랙이 이미 있으면 올리지 않는다.** 사람이 손으로 올린 트랙을 덮어쓰지 않고, 다시 실행해도 트랙이 늘지 않는다. 우리가 올린 트랙 ID는 게시 기록에 남겨 그 전에 걸러낸다.
- `sync=False`로 우리 시각을 그대로 쓴다. 켜면 YouTube가 음성에 맞춰 타이밍을 다시 잡아 구워진 자막과 어긋난다.
- 트랙은 **처리가 끝난 뒤, 예약보다 먼저** 올린다. 공개 시점에는 자막이 이미 붙어 있어야 한다.
- **자막 실패는 게시를 실패로 만들지 않는다.** 영상은 이미 올라가 있어 되돌릴 수 없다. 무엇이 왜 안 됐는지를 게시 기록(`checkpoint.captions`)과 목록 응답에 남겨 사람이 판단하게 한다. 조용히 넘어가지도, 되돌리지도 않는다.
- 언어를 모르면(자동 감지에 맡긴 원어 작업, 편집본의 `und`) 올리지 않고 그 이유를 남긴다. 언어를 추측해 붙이지 않는다.
- 게시 전 점검(`scripts/preflight_publish.py`)이 트랙을 켠 경우에만 `youtube.force-ssl` 권한을 함께 본다. 없으면 영상은 올라가고 자막만 조용히 실패한다.


## 외부 자막 파일 반입 (2026-09-19)

- 형식을 사람이 고르게 하지 않는다. pysubs2가 글자를 보고 SRT·WebVTT·ASS를 판별한다. 확장자는 틀릴 수 있고, 사람이 고르게 하면 틀렸을 때 실패 이유가 엉뚱해진다.
- 꾸밈 표기(기울임·색·위치·화자 태그)는 벗기고 글자만 남긴다. 그것은 그 도구가 그 화면에 맞춰 정한 모양이고, 우리 화면 모양은 우리 표시 규칙이 정한다.
- **파일의 줄바꿈도 버린다.** 공백으로 합쳐 한 줄로 만든 뒤 렌더가 우리 규칙으로 다시 끊는다. 남겨 두면 두 도구의 줄 규칙이 섞인다.
- **뺀 자막은 조용히 버리지 않는다.** 글자가 없거나 시간이 올바르지 않거나 너무 긴 자막은 빼되, 몇 번째 자막을 왜 뺐는지 응답에 담아 사람이 본다.
- 들인 자막은 **대본 새 버전**이 된다. 직접 편집과 같은 저장 경로(`save_transcript`)를 쓰므로 원본 길이 검사와 가독성 보고가 똑같이 적용되고, 기존 버전은 감사용으로 남는다.
- **시각은 파일에 적힌 그대로 쓴다.** 원본 음성과 맞는지는 확인하지 않는다. 자동으로 맞추려면 ffsubsync 같은 보정이 필요한데, 들인 자막이 실제로 얼마나 어긋나는지 재 본 적이 없다. 재기 전에 넣으면 맞는 자막을 흔들 수 있다. 지금은 어긋날 수 있다고 알리고 사람이 확인하게 한다.


## 자막 파일 인코딩 (2026-09-19)

- 파일은 **바이트 그대로** 받는다. 브라우저가 글자로 먼저 바꾸면(`file.text()`는 UTF-8로 읽는다) UTF-8이 아닌 파일이 그 자리에서 깨져 서버는 손쓸 수 없다.
- 스스로 판단하는 범위는 **파일이 밝힌 표시(BOM)와 UTF-8까지**다. 거기서 실패하면 **추측하지 않는다.** 인코딩을 잘못 고르면 글자가 조용히 깨진 채로 저장되고, 나중에 영상에 그대로 구워져 올라간다. 되돌릴 수 없는 실패다.
- 대신 후보마다 **첫 자막이 어떻게 보이는지** 붙여 돌려준다. 이름(CP949·EUC-KR·Shift_JIS)만 보고는 고를 수 없어도, 자기 자막 글자는 알아본다. 판단을 사람에게 넘기되 판단할 근거를 준다.
- 자막으로 읽히지 않는 후보는 내놓지 않는다. 고를 수 없는 선택지를 늘어놓으면 고르기만 어려워진다.
- 같은 글자가 나오는 후보는 한 번만 보여 준다(CP949는 EUC-KR을 포함해 결과가 같다).
- ~~자동 판별 라이브러리(chardet·charset-normalizer)는 넣지 않았다. 그것도 추측이고, 틀렸을 때 사람이 알아차릴 방법이 없다. 미리보기는 틀린 추측을 사람이 바로 본다.~~ 사용자 요청으로 넣었다. 아래 절에서 다룬다.


## 자막 인코딩 자동 판별 (2026-09-19)

- 사용자 요청으로 자동 판별을 넣는다. 앞 절에서 "추측하지 않는다"고 적었으므로, **판별을 쓰되 무엇으로 읽었는지 밝히고 되돌릴 수 있게** 붙인다.
- **charset-normalizer**를 쓴다. chardet은 LGPL이라 우리 코드에서는 쓰지 않는다. 이 저장소의 나머지 의존성은 MIT·BSD·Apache라 라이선스 조건이 하나 늘어나는 것을 감수할 이유가 없다.
- 다만 **chardet이 아주 없어지지는 않는다.** 선택 extra인 `[subtitles]`의 ffsubsync가 chardet을 의존성으로 끌어온다. 우리가 부르지는 않지만 워커 이미지에는 들어간다. 배포물 라이선스를 따질 때 이 사실을 빼놓지 않는다.
- 순서는 **BOM → UTF-8 → 판별기**다. BOM과 UTF-8은 추측이 아니므로 판별기보다 앞에 둔다.
- 판별기 결과는 그대로 쓰지 않는다. 그 인코딩으로 읽은 글자가 **자막으로 읽히는지** 확인한다. 읽히지 않으면 판별이 틀린 것이므로 후보 목록으로 넘어간다.
- **이 확인은 글자가 깨진 것까지 걸러내지 못한다.** 한국어 자막을 cp1252로 읽으면 글자는 깨져도 시간 줄은 멀쩡해서 자막 파일로 읽힌다. 그래서 확인에만 기대지 않는다.
- 대신 **판별로 읽었다는 사실을 남긴다.** API가 `encoding`과 `encoding_detected`를, 판별일 때는 다른 후보(`choices`)까지 돌려주고, 편집기는 "무엇으로 읽었으니 글자를 확인하라"고 띄우며 다른 인코딩으로 다시 들이는 버튼을 함께 보여 준다. 다시 들이면 대본 새 버전이라 원래 것이 남는다.
- 판별기는 **핵심 의존성**이다(선택 extra가 아니다). 없을 때 조용히 옛 동작으로 돌아가면, 같은 파일이 환경에 따라 다르게 처리된다.


## 자막 싱크 보정 (2026-09-19)

- 사용자 요청으로 ffsubsync를 넣는다. 앞서 "얼마나 어긋나는지 재기 전에는 넣지 않는다"고 적었으므로, **보정과 함께 그 보정을 재는 검증을 같이 넣는다.** `scripts/verify_sync.py`가 아는 만큼 밀어 둔 자막이 돌아오는지와, **이미 맞는 자막이 흔들리지 않는지**를 CI에서 잰다. 후자가 이 기능에서 가장 나쁜 실패다.
- 자동으로 적용하지 않는다. 사람이 버튼을 눌러야 돌고, 결과는 **새 대본 버전**이다. 기존 버전이 남으므로 보정이 틀려도 되돌릴 수 있다.
- 얼마나 옮겼는지(`offset_seconds`)를 작업 결과에 남기고 화면에 보여 준다. 보정기가 무엇을 했는지 모르면 사람이 판단할 수 없다.
- 보정기가 맞추지 못했다고 하면(`sync_was_successful=False`) 결과를 쓰지 않는다. 엉뚱한 값으로 맞는 자막을 흔드는 것보다 안 하는 편이 낫다.
- **글자는 보정기에서 돌려받지 않는다.** 시각만 가져와 원래 자막에 붙인다. 보정기는 자막을 다시 쓸 수 있지만 대본은 사람이 정한 것이다.
- 보정기에 넘기는 자막은 표시 규칙을 거치지 않은 **날것**이다(`dump_subtitles`). 규칙을 적용하면 자막이 나뉘어 개수가 달라지고, 돌아온 시각을 원래 자막에 도로 맞출 수 없다.
- 파이썬 API(`ffsubsync.ffsubsync.run`)를 쓴다. CLI로 부르면 오프셋을 로그에서 긁어야 한다. API는 그 값을 그대로 돌려준다.

## 2026-09-19: 자막 템플릿과 자막 파일 도구

- 자막 모양을 렌더 코드의 고정값에서 `pipeline/subtitle_templates.py`의 `SubtitleTemplate`(pydantic, JSON 왕복)로 옮겼습니다. 내장 `default`는 이전 고정값과 같아 기존 편집본의 모양이 바뀌지 않습니다.
- 색은 CSS식 `#RRGGBB[AA]`(AA=불투명도)로 받고 ASS 알파(0=불투명)로 바꿉니다. 사람이 적는 값은 CSS 관행이 익숙하고, ASS 표기는 pysubs2가 씁니다.
- 글꼴 이름에 쉼표·중괄호·역슬래시를 막습니다. ASS 스타일 줄은 쉼표 구분이고 중괄호는 명령이라, 자막 글자에 하던 것과 같은 이유로 템플릿 값에서도 주입을 막습니다.
- 세로 여백은 픽셀이 아니라 화면 높이 비율(`margin_vertical_ratio`)입니다. 숏폼(1920)과 가로 영상(1080)에 같은 템플릿을 쓰기 위해서입니다. 좌우 여백은 기존과 같이 픽셀입니다.
- 화면 제목은 자막의 반대쪽 끝에 둡니다. 같은 쪽에 두면 줄이 늘 때 겹칩니다.
- `EditSpec.font_size`는 선택값이 되었습니다. 비우면 템플릿 크기, 적으면 그 값이 우선합니다. 옛 기록의 `font_size: 64`는 그대로 읽혀 결과가 같습니다.
- 서버에는 내장 템플릿만 두고 사용자 JSON 템플릿은 명령줄 전용입니다. 업로드·저장 화면을 만들면 검증·버전·승인 범위가 넓어지므로 필요가 확인될 때까지 미룹니다.
- 명령줄 도구 `pipeline/subtitle_tool.py`(`r4-subtitles`)는 서버와 같은 읽기·규칙·템플릿 코드를 부릅니다. 따로 구현하면 서버 렌더와 결과가 달라질 수 있어 계산 코드를 공유하고 CLI는 인자 처리와 파일 입출력만 합니다.

## 2026-09-20: 트렌디 자막 템플릿 팩과 글꼴

- 인스타그램에서 파는 브이로그 자막 템플릿(파스텔 상자, 네온, 픽셀, 통통 외곽선, 손글씨)을 참고해 내장 템플릿을 38종으로 늘렸습니다. 모두 libass가 그릴 수 있는 값(글꼴·색·외곽선·BorderStyle·`\blur`·장식 글자)만 씁니다. 그라디언트·애니메이션·이모지는 libass가 못 그리므로 넣지 않았습니다.
- 글꼴은 저장소에 넣지 않고 빌드 때 받습니다. Google Fonts 저장소와 Galmuri 저장소의 **커밋 해시 고정 URL**과 SHA-256으로 같은 바이트를 보장합니다. 모두 OFL-1.1이라 영상 배포에 제약이 없습니다. 파일 안 family 이름이 Google Fonts 이름과 다른 경우(Nanum Pen, Galmuri11 Regular)가 있어 libass가 조용히 대체하는 사고를 막으려고 내려받기와 CLI가 `fc-scan`/`fc-match`로 이름을 확인합니다.
- 상자 색은 `box_color`로 분리했습니다. libass는 BorderStyle 3 상자를 외곽선 색으로 채우므로 뒷색에만 넣던 이전 `box` 템플릿은 실제로 불투명 검정 상자였습니다. 이번에 고쳤고 시트 렌더로 확인했습니다.
- 미리보기 시트는 PNG 이미지 합성이 아니라 ASS 한 파일에 `\pos`로 격자를 놓고 FFmpeg 한 프레임으로 그립니다. 실제 렌더와 같은 경로라 시트가 곧 검증입니다. CI가 워커 이미지에서 시트를 만들어 artifact로 남깁니다.
- 관리화면 미리보기는 CSS 근사(Google Fonts CSS + `text-shadow`)입니다. 브라우저에서 libass를 돌리는 방법(JASSUB)은 별도 PR #21이 시도했으며, 이 PR은 의존성을 늘리지 않는 쪽을 택했습니다.

## 2026-09-20: 스티커 이중 외곽선과 글꼴 확대

- 참고 이미지의 핵심 모양(안쪽 색선 + 바깥 흰 테두리)은 ASS 스타일 하나로는 못 그립니다. 이벤트를 두 겹(layer 0 굵은 바깥 테두리, layer 1 원래 선)으로 내는 방식을 택했습니다. 렌더 비용은 두 배지만 자막은 프레임당 몇 개뿐이라 무시할 만합니다. 그림자·글로우는 뒤 층에만 둬 앞 글자를 또렷하게 유지합니다.
- 글꼴을 16종에서 29종으로 늘렸습니다. 용량이 큰 것(Stylish 10MB, Black And White Picture 9MB, Gowun Dodum 7MB)은 뺐습니다. 워커 이미지는 약 30MB 늘어납니다.
- 시트의 글자 크기 맞춤은 실제 렌더 폭을 재지 않고 글꼴별 폭 계수로 어림합니다. 정확하지 않아도 칸을 넘치지 않는 것이 목적이고, 실제 영상에는 영향이 없습니다.

## 2026-09-20: Google Fonts 밖의 굵은 한글 글꼴

- 참고 이미지의 "썸네일 글씨" 느낌은 잘난체·카페24 써라운드 같은 굵고 둥근 글꼴에서 옵니다. Google Fonts에는 이 계열이 거의 없어 각 회사가 무료로 배포하는 글꼴을 추가했습니다. 모두 상업 사용과 영상 삽입을 허용하지만 OFL이 아니라 수정·판매가 금지되므로 라이선스 URL을 목록에 함께 둡니다.
- 파일은 회사 사이트의 zip이 아니라 눈누(projectnoonnu)가 GitHub에 올린 WOFF를 커밋 고정으로 받습니다. 같은 바이트를 보장할 수 있는 유일한 출처였습니다. libass는 WOFF를 직접 못 읽으므로 설치 때 fontTools로 TTF/OTF로 바꿉니다. 체크섬은 원본 WOFF로 확인하고 변환 결과 옆에 원본 해시를 남깁니다.
- 티머니 둥근바람·카페24 당당해는 고정할 수 있는 출처를 찾지 못해 넣지 않았습니다.
- jsDelivr CDN은 이 세션의 프록시가 막아 확인하지 못했고, raw.githubusercontent.com만 씁니다.

## 2026-09-20: 속 빈 네온·입체 돌출·단어별 강조

## 2026-09-20: 둥근 상자는 글자 폭을 재서 벡터로 그린다

- libass 상자(BorderStyle 3·4)는 모서리가 각집니다. 참고 이미지의 알약 모양 상자를 만들려면 글자 뒤에 도형을 따로 그려야 하고, 그러려면 ASS를 만드는 시점에 글자 폭을 알아야 합니다. 설치된 글꼴 파일의 advance 폭을 fontTools로 더하는 방식을 택했습니다. libass가 그리는 폭과 거의 같고(커닝 없는 한글 글꼴), 실제 렌더로 확인했습니다.
- 글꼴을 못 찾으면 어림값으로 그립니다. 어긋날 수 있다는 것을 `measured=False`로 알리고 문서에 적습니다. 워커 이미지에서는 항상 글꼴이 있습니다.

## 2026-09-20: 이모지는 흑백 글꼴을 구간마다 명시한다

- libass는 컬러 이모지 글꼴을 못 그립니다. 글꼴 대체에 맡기면 어느 글꼴이 걸릴지 환경마다 달라(로컬에서는 픽셀 글꼴의 이모지가 나왔습니다) 이모지 구간에 `\fn`으로 Noto Emoji(OFL, 흑백)를 명시합니다. 컬러 이모지가 꼭 필요하면 이미지 오버레이가 필요하고 이번 범위 밖입니다.
- 시트의 흐름 배치는 글꼴 메트릭(둥근 상자와 같은 코드)으로 항목 폭을 재서 한 줄에 채웁니다. 격자보다 글자가 크고 밀도가 높아 참고 이미지에 가깝습니다.

## 2026-09-20: 움직이는 자막은 ASS 애니메이션 명령으로 만든다

- 참고 템플릿 팩의 "움직이는 자막"(팝·바운스·타자기·단어별 등장·노래방 강조)은 별도 모션 그래픽 도구 없이 libass가 지원하는 ASS 명령(`\t`, `\move`, `\fad`, `\fscx`/`\fscy`, `\frz`, `\alpha`)만으로 만듭니다. 렌더 경로(FFmpeg `subtitles` 필터)가 그대로이고 자막 파일(SRT·VTT)에는 영향이 없습니다.

- 노래방·단어별 등장의 단어 시각은 자막 길이를 고르게 나눈 어림값입니다. 단어 타임스탬프 연결은 다음 작업입니다. 둥근 상자는 글자와 같은 정렬점 기준으로 놓아(`\an`) 크기·회전·이동이 글자와 같은 점을 중심으로 일어납니다.

## 2026-09-20: 그라데이션은 clip 띠로, 컬러 이모지는 COLR 층 겹침으로 그린다

- ASS에 그라데이션이 없어 색을 바꾼 같은 글자를 `\clip` 사각형 24개로 잘라 겹칩니다. 띠가 겹치지 않아 반투명 문제가 없고 이벤트 수만 늘어납니다. 띠 위치는 둥근 상자와 같은 글꼴 메트릭으로 잽니다. libass가 같은 층의 동시 이벤트를 위로 쌓는(충돌 회피) 탓에 띠가 밀려 보이지 않던 것을 `\pos` 고정으로 해결했습니다. 대안(FFmpeg에서 텍스트 마스크에 그라데이션 합성)은 자막 경로가 둘로 갈려 택하지 않았습니다.
- libass는 컬러 이모지 글꼴을 못 그립니다. 이미지 오버레이 대신 COLRv0 글꼴(Twemoji Mozilla)의 색 층이 보통 윤곽선 글리프라는 점을 써서, 층마다 사용자 영역 코드를 주고 폭을 0으로 만든 글꼴을 만들고 자막에서 `{\1c}층…자리표`로 겹칩니다. 자막 렌더 경로 하나로 끝나므로 외곽선·움직임·타자기가 이모지에도 그대로 적용됩니다. 이미지 오버레이는 위치를 따로 계산해야 하고 움직임을 따라가지 못해 택하지 않았습니다. Noto Color Emoji는 CBDT 비트맵(변환 불가)·COLRv1(그라데이션 층)이라 COLRv0인 Twemoji를 골랐고, CC-BY 출처 표기가 필요합니다.

## 2026-09-20: 단어 시각·브라우저 정확 미리보기·스티커

- 노래방·단어별 등장은 정렬기(whisper)의 단어 시각을 `Cue.words`로 실어 씁니다. 대본 DB에 `words` JSON 열을 두고 API·편집기·렌더까지 그대로 넘기며, 사람이 글자를 고친 자막은 `words`를 비워 어긋난 시각을 쓰지 않습니다. 표시 규칙이 자막을 나눌 때는 정렬기의 줄 묶기와 같은 규칙(공백 뺀 글자 수)으로 단어를 나눕니다.
- 편집기 정확 미리보기는 CSS 근사 대신 libass WASM(jassub, MIT)으로 워커와 같은 ASS를 그립니다. 글꼴은 API에서 받습니다(API 이미지에도 같은 글꼴 설치). 브라우저 libass는 fontconfig 없이 name 테이블의 family(nameID 1)로만 찾으므로, 받은 글꼴의 family 이름을 템플릿 이름과 같게 정리합니다("Pretendard Black" → "Pretendard"). 교차 출처 격리 헤더는 넣지 않아 단일 스레드로 동작합니다(Google Fonts CSS·MinIO 미리보기와의 충돌을 피함).
- 스티커는 내장 도형을 ASS 드로잉으로 그려 자막과 같은 경로(움직임 포함)를 쓰고, PNG는 FFmpeg overlay로 합성 단계에서 얹습니다. 도형 크기는 `\fscx` 대신 좌표를 곱해 정해 팝·맥박 같은 크기 움직임과 겹치지 않게 합니다. 이미지 업로드 화면은 두지 않고 워커 디렉터리에 미리 넣는 방식입니다.

## 2026-09-21: 모션 프리셋은 동작 목록(데이터)으로 적는다

- 참고한 편집 프리셋 팩(프리미어 프로용 "모션 프리셋" 90여 종)처럼 움직임을 한 벌씩 고르게 하되, 종류마다 코드를 늘리는 대신 **동작(step) 목록**을 데이터로 적고 컴파일러가 ASS 명령으로 바꿉니다(`pipeline/subtitle_presets.py`). 그래서 새 움직임은 JSON 한 장이면 되고(`R4_PRESETS_DIR`, `presets new`), 편집기·API·CLI·정확 미리보기가 모두 같은 코드로 그립니다. 대안(프리셋마다 함수)은 93종에서 코드가 그만큼 늘고 사용자가 만들 수 없어 택하지 않았습니다.
- 동작은 `in`(등장)·`out`(사라짐)·`hold`(계속) 세 구간이고, `hold`는 등장이 끝난 뒤 시작해 같은 값을 건드리는 명령끼리 싸우지 않게 했습니다. ASS가 이벤트당 `\move` 하나만 허용하므로 `move` 동작도 하나로 막습니다.
- **반복 이동**(둥둥 뜨는·통통·떨림)은 `\pos`를 `\t`로 바꿀 수 없어, `\org`을 글자에서 4000px 떨어뜨리고 `\frz`를 0.2° 안팎으로 흔들어 호(弧)로 흉내 냅니다. 반지름이 크면 거의 직선이고 기울기도 눈에 띄지 않습니다(렌더로 14~28px 진폭 확인). 대안(자막을 여러 이벤트로 쪼개 `\move`를 잇기)은 줄 정렬·그라데이션 띠·상자 층이 모두 어긋나 택하지 않았습니다.
- 조각별 동작(글자·단어)은 움직임 모듈의 토큰 나누기(`run_slots`)와 `\r` 되돌리기를 그대로 씁니다. 타자기·단어별·노래방은 이미 검증된 `animate_runs`에 그대로 넘기고, 물결·글리치만 프리셋 쪽에서 만듭니다. 조각마다 명령이 두 번 붙으면 서로 덮어쓰므로 조각별 동작도 하나로 막습니다.
- 동작의 `amount`는 비움(None)과 `0`을 구분합니다. 처음에는 `amount or 기본값`으로 썼는데 "크기를 0으로"(아무것도 없는 데서 펼쳐짐)가 기본값 40%로 바뀌어 상하 등장·펼치기가 의도와 달랐습니다. 크기 0은 libass가 줄 높이를 잃지 않게 1%로 바닥을 둡니다.
- 계속되는 동작이 만드는 `\t` 수에 상한을 두고(자막이 길면 주기를 늘림) `in-out` 가속은 한 주기에 `\t`를 둘 쓰므로 상한을 절반으로 잡습니다. 파일이 커지면 libass 파싱이 느려집니다.

## 2026-09-21: 자막은 글자 수가 아니라 말한 시각으로 끊는다

- 상용 숏폼 자막이 "퀄리티 있어" 보이는 가장 큰 이유는 글꼴이 아니라 **리듬**입니다. 말이 바뀔 때 자막도 바뀌면 전문적으로 보이고, 두 줄짜리가 5초 떠 있으면 방송 자막처럼 보입니다. 그래서 자막을 끊는 기준을 글자 수에서 **단어 시각**(`Cue.words`)으로 옮겼습니다. 단어 시각은 이미 정렬기 → 대본 DB → 렌더까지 흐르고 있었고 노래방·단어별 등장에만 쓰이고 있었습니다.
- 다만 기본값은 바꾸지 않습니다. 끊는 방식을 `broadcast`(지금까지)와 `shortform`으로 나눠 고르게 했고, 단어 시각을 쓸지는 규칙(`SubtitleRules.use_word_timings`)에 적어 둡니다. 기본값을 바꾸면 이미 만든 편집본의 렌더 결과가 전부 달라져 사람이 승인한 자막과 올라가는 자막이 달라집니다.
- 단어 시각이 없거나(자막 파일 입력) 사람이 글자를 고쳐 단어와 맞지 않으면 글자 수 방식으로 조용히 돌아갑니다. 글자를 지우거나 시각을 지어내지 않습니다.
- 끊은 자리를 두 가지로 다듬습니다. 뒤 말을 꾸미는 짧은 말(그·이·안·못·잘 …)이 자막 끝에 혼자 남으면 다음 자막으로 넘기고, 자막 끝은 다음 자막 시작까지 최대 0.4초 띄워 깜빡임을 없앱니다. 형태소 분석기를 새로 들이는 대신 목록 하나로 처리했습니다. 한국어에서 이 부류는 닫힌 집합에 가깝고, 틀려도 한 자막이 조금 길어질 뿐입니다.
- 좋아졌는지는 `quality`(자막 장수·표시 시간·읽기 속도·규칙 위반 비율)로 잽니다. 숫자가 없으면 "좋아진 것 같다"에서 끝납니다.

## 2026-09-21: 용어집은 번역 전에 원문에 박아 넣는다

- 채널 이름·제품명처럼 매번 같게 나와야 하는 말이 문장마다 다르게 번역되는 문제를 용어집으로 고정합니다. 뜻을 고치는 장치가 아니라 **표기를 고정**하는 장치입니다. 이미 있던 `glossaries` 테이블과 `glossary_version` 해시 항목은 어디에도 연결되어 있지 않았습니다.
- Google 번역은 `text/plain`으로 보낸 글에서 일부 구간만 건너뛰게 할 수 없습니다. 건드리지 말 구간은 `text/html` + `translate="no"`로만 표시할 수 있습니다. 그래서 용어 자리를 **목표 언어 표기로 바꿔 놓고** 그 자리만 감싸 보냅니다. 번역이 끝나면 표시를 걷어냅니다.
- 용어가 하나도 걸리지 않은 문장은 지금까지와 똑같이 `text/plain`으로 보냅니다. 한 배치가 두 요청으로 갈리지만 글자 수는 그대로이고, **번역 경로를 바꾸지 않는 문장은 결과도 그대로**입니다. 모든 문장을 HTML로 보내면 용어 없는 문장까지 escape·복원을 거치게 되어 택하지 않았습니다.
- Google은 표시 글자도 세어 청구합니다. 그래서 예산 계산(`paid_estimate`)도 **보낼 글자 그대로** 셉니다(`protect()`를 한 번 돌려 길이를 잽니다). 원문 길이로 잡으면 예약이 실제 청구보다 적어집니다. 걸린 자리마다 28자 + 원문·번역 표기의 길이 차만큼 더 나옵니다.
- Google 자체 용어집(`glossaryConfig`)이 품질로는 낫습니다(어미 변화 처리, 표시 글자 없음). 다만 용어 파일을 **Cloud Storage**에 두고 `global`이 아닌 지역에 리소스를 만들어야 하는데 이 저장소의 객체 저장소는 S3 호환(MinIO)입니다. 그래서 리소스 이름(`R4_GOOGLE_TRANSLATE_GLOSSARY`)이 설정되어 있으면 그쪽을 쓰고, 아니면 위 방식을 씁니다. 둘을 섞지 않습니다.
- 용어가 번역문에서 사라져도 **번역을 버리지 않습니다.** 용어가 빠진 번역이 깨진 번역보다 낫습니다. 대신 몇 개가 사라졌는지 세어 기록하고, `verify_translate.py --glossary`가 그 수치를 냅니다.
- 원문 언어를 지정하지 않은(자동 감지) 작업에는 적용하지 않습니다. 어느 방향의 용어집인지 알 수 없어 엉뚱한 용어집을 들이대느니 쓰지 않는 쪽이 낫습니다.
- 찾기는 대소문자를 가리고 겹치는 용어는 긴 쪽이 이깁니다. 어미 변화·대소문자 변형까지 맞추려면 형태소 분석이 필요한데, 그 복잡도 대신 "필요하면 두 줄 적는다"를 택했습니다.

## 2026-09-21: 문맥은 합쳐서 번역하고, 어색한 자막만 다시 쓴다

- 자막이 말하는 속도에 맞춰 잘려 있어 번역기가 **문장의 절반만** 보고 옮기고 있었습니다. 숏폼 끊기를 켜면 더 심해집니다. 그래서 이어지는 조각을 한 문장으로 합쳐 번역하고, 번역문을 각 자막이 떠 있던 시간에 비례해 다시 나눕니다.
- **구분 표시를 끼워 넣지 않습니다.** Google이 `text/html`에서 태그를 지켜 주므로 자막마다 태그를 둘러 다시 쪼개는 방법도 되지만, Google은 태그 글자도 세어 청구합니다(자막마다 7자 이상). 한국어 자막은 짧아서 그 비율이 큽니다. 합쳐 보내고 우리가 나누면 **글자 수가 늘지 않습니다.**
- 다시 나누기는 낱말 경계에서만 합니다. 낱말이 자막 수보다 적으면 글자를 쪼개 단어가 두 자막에 걸치므로, 그때는 나누기를 포기하고 그 묶음만 조각별로 다시 번역합니다. 띄어쓰기가 없는 언어(일본어·중국어 등)만 글자로 나눕니다.
- **더빙에는 쓰지 않습니다**(작업을 만들 때 거부합니다). 더빙은 자막 조각이 곧 그 구간의 발화라 문장을 다시 나누면 말과 글이 어긋납니다. 자막 경로에만 씁니다.
- LLM 재번역은 **전체가 아니라 몇 군데만** 합니다. 전체를 맡기면 값이 몇 배가 되는데, 기계 번역은 대부분의 문장에서 충분하고 문제는 몇 군데에 몰립니다. 고르는 일은 외부 호출 없이 원문·번역문의 겉모양만으로 합니다(원문 그대로·비어 있음·길이 이상·같은 말 반복·용어 누락·문장 조각).
- 길이 기준을 고정하지 않고 **그 묶음의 중앙값**에서 잡습니다. 언어쌍마다 늘어나는 비율이 달라 고정값은 한쪽 언어에서만 맞습니다. 표본이 4개 미만이면 넉넉한 고정 범위로 돌아갑니다.
- 다시 쓰는 수에 상한을 둡니다(최대 30%, 최대 20개). 비용이 번역량에 비례해 뛰지 않게 하려는 것이고, 예산 계산도 같은 상한을 씁니다. 상한이 없으면 "어색함" 판정이 느슨해질 때 요금이 함께 뜁니다.
- **다시 쓰기에 실패해도 자막을 버리지 않습니다.** 응답이 JSON 배열이 아니거나 개수가 다르면 기계 번역을 그대로 쓰고 단계 결과에 사유를 남깁니다. 번역이 조금 어색한 것보다 작업이 통째로 막히는 쪽이 나쁩니다.
- LLM은 SDK 대신 `httpx`로 부릅니다. ElevenLabs·Sync와 같은 모양이라 클라이언트를 갈아 끼워 계약 테스트를 할 수 있고 의존성이 늘지 않습니다. 모델 이름에는 기본값을 두지 않습니다. 이름은 바뀌고, 무엇을 부를지는 사람이 정할 일입니다.


## 2026-09-21: 문맥 배치와 LLM 재번역을 기본으로 켠다

- 사용자가 "네가 켜"라고 해서 둘 다 기본값을 켬으로 바꿨습니다. 켜 두려면 **켜 둬도 안전해야** 하므로 기본값을 바꾸기 전에 두 가지를 먼저 고쳤습니다.
- **문장부호가 거의 없는 대본은 묶지 않습니다**(`punctuated`, 자막의 15% 미만이 문장부호로 끝나면 묶지 않음). 전사가 문장부호를 내지 않으면 어디서 문장이 끝나는지 알 수 없고, 그때 묶으면 **서로 다른 문장을 붙여** 번역합니다. 조각별 번역보다 나쁩니다. 켜 두는 기본값이 되는 순간 이 경우가 모든 작업에 닥치므로 판단을 막아 두었습니다. 15%는 잰 값이 아니라 정한 값입니다.
- **더빙은 거부 대신 끕니다.** 켜짐이 기본값이면 `audio_mode="dub"`으로 작업을 만들 때마다 검증 오류가 납니다. 기능이 안 맞는 것은 사람의 잘못이 아니므로 막지 않고 조용히 끕니다(워커도 같은 판단을 합니다).
- **LLM 설정이 없으면 조용히 건너뜁니다.** 켜짐이 기본값인데 설정이 없다고 오류를 남기면, LLM을 쓸 생각이 없는 사람의 모든 작업에 오류 표시가 붙습니다. 화면은 `/workflow/configuration`의 `llm_translate_configured`로 이미 상태를 보여 줍니다. 단가만 빠진 경우(키·모델은 있음)는 그대로 Blocked입니다. 돈이 나가는 길에 상한이 없는 것은 설정 실수이지 "쓰지 않겠다"가 아닙니다.
- 기본값이 바뀌어도 **이미 만든 결과물은 바뀌지 않습니다.** 작업 옵션은 작업을 만들 때 굳고, 다시 만들지 않는 한 과거 결과물과 승인은 그대로입니다.


## 2026-09-21: 무음 컷은 직접 구현하고, MoviePy는 넣지 않는다

- 사용자가 FFmpeg·MoviePy·Auto-Editor·PySceneDetect를 검토 대상으로 주었습니다. FFmpeg와 PySceneDetect는 이미 쓰고 있었고, **MoviePy는 넣지 않았습니다.** FFmpeg를 파이썬으로 감싼 것인데 이 저장소는 이미 필터 체인을 직접 조립합니다. 한 겹이 더 생기고 프레임을 파이썬 메모리로 올렸다 내리는 구간이 생겨 긴 영상에서 느려집니다. MoviePy라야 되는 일이 보이지 않았습니다.
- **Auto-Editor는 의존성으로 넣지 않고 같은 일을 직접 구현했습니다**(`pipeline/trimming.py`). 발화 구간을 찾는 쪽은 이미 있었고(`speech_spans`), 없던 것은 자르는 쪽입니다. 외부 도구를 부르면 자막·단어 시각·스티커를 새 시간축으로 옮기는 일은 어차피 우리가 해야 하는데, 그 계산이 이 기능의 전부입니다. 의존성만 늘고 얻는 것이 없습니다.
- 자르기는 `select`/`aselect` + `setpts`로 **한 번의 FFmpeg 호출** 안에서 합니다. `trim`+`concat`으로 토막마다 갈래를 만드는 방법도 되지만 스티커 오버레이 그래프와 얽혀 복잡해집니다. 대신 `setpts=N/FRAME_RATE/TB`는 프레임률이 일정하다고 보므로 VFR 원본에서는 어긋날 수 있습니다(아직 재지 않았습니다).
- **자막을 쪼개지 않습니다.** 한 자막이 잘린 자리를 걸치면 남은 부분의 처음부터 끝까지로 둡니다. 쪼개려면 글자도 쪼개야 하고, 말이 있는 곳만 남기므로 걸치는 경우 자체가 드뭅니다.
- 단어 시각은 하나라도 잘려 나가면 전부 버립니다. `pipeline.editing._clip_words`와 같은 판단입니다. 맞지 않는 단어 시각은 없는 것보다 나쁩니다.
- 숏폼 구간 추천은 **장면 경계와 발화 구간만** 봅니다. 화면 내용이나 말의 뜻은 보지 않습니다. 비중(말 0.60 / 전환 0.25 / 자리 0.15)은 잰 값이 아니라 정한 값이며, 순위를 매기는 데 쓰는 것이지 근거가 아닙니다. 말이 35%도 차 있지 않으면 후보로 보지 않으므로 말하는 영상에서만 씁니다.
- 후보는 장면 경계에서 시작하고 끝납니다. 임의의 시각에서 자르면 화면과 말이 중간에서 끊깁니다. 장면 전환이 없는 영상에서는 목표 길이의 절반 간격으로 후보를 만듭니다.


## 2026-09-21: 얼굴은 따라가되 떨지 않게, 잡음은 내장 필터부터

- 세로 자르기의 중심이 사람이 고른 고정 숫자(`focus_x`) 하나였습니다. 얼굴 위치를 따라가게 했지만 **검출 결과를 그대로 쓰지 않습니다.** 얼굴 상자는 프레임마다 흔들리고 검출이 한 번 실패하면 중심이 튑니다. 작은 움직임은 무시하고(`deadzone`), 움직일 때도 속도를 제한하고(`max_speed`), 못 찾은 구간은 마지막 위치를 유지합니다. 떨리는 화면은 안 따라가느니만 못합니다.
- **세로(y)는 건드리지 않습니다.** 16:9 → 9:16에서는 세로가 거의 그대로라 얻는 것이 적고, 위아래로 흔들리면 더 눈에 띕니다.
- FFmpeg `crop`의 x를 시간의 식으로 넘깁니다. 구간을 `gte(t,a)*lt(t,b)`로 나눕니다. `between()`은 양끝을 모두 포함해 경계에서 두 구간이 함께 더해지고 그 한 프레임만 값이 튑니다. 꼭짓점은 40개까지 솎습니다.
- **`crop`은 무음 컷(`select`) 뒤에 옵니다.** 그래서 얼굴 시각도 잘린 뒤의 시각으로 옮깁니다(`clip_path`). 두 기능이 같은 시간축을 쓰도록 `trimming.moved`를 함께 씁니다.
- 검출기는 **MediaPipe 우선, OpenCV 내장 대체**입니다. MediaPipe가 정확하지만 설치가 크고 판올림마다 API가 바뀝니다. OpenCV는 `scenedetect`가 이미 끌고 오고 모델이 패키지 안에 있어 내려받을 것이 없습니다. 어느 쪽을 썼는지 결과에 적어 둡니다(조용히 품질이 달라지지 않게).
- 잡음 제거는 **FFmpeg 내장 `afftdn`부터** 씁니다. DeepFilterNet이 더 잘 깎지만 파이토치 계열이라 워커 이미지가 크게 늘어납니다. 의존성 0으로 먼저 재 보고 모자라면 그때 붙이는 순서입니다. 무음 컷과 함께 쓸 때는 **자르기가 먼저**입니다(버릴 구간까지 깎는 것은 헛일입니다).


## 2026-09-21: 자동으로 자른 결과는 사람이 고칠 수 있어야 한다

- 무음 컷이 "알아서 자르고 끝"이면 결과를 렌더해 봐야 압니다. 그래서 자르기 전에 재 보는 무료 작업(`silence`)을 두고, 잰 토막을 편집기에서 켜고 끌 수 있게 했습니다. LosslessCut의 컷 목록 편집에서 가져온 얼개입니다(그 앱은 라이브러리가 아니므로 붙인 것이 아닙니다).
- 사람이 고친 목록은 `EditSpec.keep`에 **명시적으로** 실립니다. 자동 탐지 설정(`silence`)보다 우선합니다. 사람이 고른 것을 기계가 다시 덮으면 화면에서 본 것과 렌더 결과가 달라집니다.
- `keep`은 모델에서 차례·겹침·구간 넘침을 검사합니다. 뒤엉킨 목록은 FFmpeg 식으로 만들면 조용히 이상한 영상이 나오므로 그 자리에서 거부합니다.
- 재 보는 것과 실제 자르기가 **같은 함수**(`trimming.keeps`)를 씁니다. 둘이 갈라지면 미리 본 것과 결과가 달라집니다.


## 2026-09-21: 전환은 렌더를 두 번 나눠서 넣는다

- `select`로 자르면 토막이 **딱 붙습니다.** 전환을 넣으려면 토막을 각각 따로 떠서(`trim`) 겹쳐야 하므로(`xfade`) 그래프가 완전히 달라집니다. 그 그래프를 기존 체인(크기·크롭·자막·스티커 오버레이)과 한 `-filter_complex`에 욱여넣으면 꼬리표가 얽혀 고치기 어려워지고, 이미 CI로 검증해 둔 경로까지 흔들립니다. 그래서 **1차에서 자르고 잇고, 2차에서 씌웁니다.** 다시 인코딩하는 만큼 화질이 깎이므로 중간 파일은 `crf 18`입니다.
- 전환을 넣으면 토막이 겹쳐 **영상이 (이음매 수 × 겹침)만큼 짧아집니다.** 그래서 시간축 매핑(`trimming.moved`)에 겹침을 넣고 자막·단어 시각·스티커·얼굴 경로가 모두 같은 값을 쓰게 했습니다. 하나라도 빠지면 글자가 말과 어긋납니다.
- 겹침은 가장 짧은 토막의 절반까지입니다. `xfade`는 토막보다 길게 겹치면 거부합니다. 그보다도 짧아지면(0.05초 미만) 전환을 포기하고 딱 붙입니다. 설정을 거부하는 대신 조용히 내려가는 쪽을 택했습니다 — 토막 길이는 사람이 정한 값이 아니라 탐지 결과라서, 그것 때문에 렌더가 실패하면 고칠 방법이 마땅치 않습니다.
- 전환 종류는 12종만 엽니다. FFmpeg에는 50여 종이 있지만 화려한 것은 숏폼에서 산만하고, 고를 것이 많다고 나아지지 않습니다.
- **GL Transitions는 쓰지 않았습니다.** GLSL 렌더 경로가 필요한데 `ffmpeg-gl-transition`은 직접 빌드하는 외부 필터라 워커 이미지 빌드가 복잡해집니다. 내장 `xfade`로 되는 것을 먼저 했습니다.
- 소리가 없는 원본에 음성 그래프를 붙이면 FFmpeg가 멈추므로 `ffprobe`로 먼저 봅니다.
