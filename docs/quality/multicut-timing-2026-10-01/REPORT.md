# 여러 컷·배속 출력 시각 검증

[PR #44](https://github.com/plutoan12/recording4/pull/44)를 main `620f19c`로 병합하고 Mac 워커에 적용했다. 검토 HEAD `7462707`과 main의 전체 파일 트리가 같으며, 코드 `c9c3590`으로 빌드한 이미지와 실행 중 이미지의 파일시스템/실행 설정 및 설치된 모듈 해시가 같다.

## 재현과 출력 규칙

기존10fps 원본의0–1초와2–6초(2배속)를 합성하면50패킷 중49프레임만 디코드됐고 비디오 길이는2.95초였다. `setpts` 이후 FPS/프레임 길이가 사라지고 혼합 배속 `concat`에서도 복구되지 않는 것을 확인했다. 구간별 FPS 복구만으로는 정상/느린 끝 구간에서 길이가 부족했다.

이어 붙인 뒤 원본 평균 FPS를 분수 그대로 적용한다. 평균이 유효하지 않을 때만 명목 FPS를 사용하고, 어느 값도 확인할 수 없으면 실패한다. 고정 FPS 출력이므로 빠른 구간은 프레임을 선택하고 느린 구간은 반복한다. 모든 원본 프레임이나 마지막 원본 프레임을 그대로 남긴다는 의미가 아니다. 최대240fps를 지원하고 단순 한 구간 경로는 유지한다.

## 회귀 검사

- 로컬 전체 **672통과/2skip**, Ruff0.8.4/포맷 통과. 기존 서드파티 경고8개가 있다.
- 신규18개는10/30/30000÷1001 FPS × 빠르게/보통/느리게 끝나는9조건, 가변 FPS1조건, FFprobe 실행 실패와 메타데이터 검증8조건이다. 먼저10개 실패와 비문자/과대 FPS2개 실패를 확인했다.
- 프레임 수·모든 표시 시각·끝 길이·오디오 존재/길이를 검사한다. 기존 모자이크 회귀도 패킷/디코드 수 및 전체 시각/FPS/길이가 같아야 통과한다.
- [최종 PR CI](https://github.com/plutoan12/recording4/actions/runs/36769160970)의 Python·웹·워커·전체 스택 통과, CodeRabbit SUCCESS/미해결 검토0. 같은 HEAD의 브랜치 Python 실행은660통과/1skip이며 선택 의존성과 DB 환경이 로컬과 다르다. 자동 검토의 기존 문서 상태 지적은 반영했다. 일반 docstring 비율 안내는 별도 경고이며 저장소 필수 린트 실패가 아니다.
- [병합한 main CI](https://github.com/plutoan12/recording4/actions/runs/36771975785)도 동일한4개 작업을 모두 통과했다. 감시 CLI의 일시적인 연결 시간 초과는 있었으나 실제 GitHub 작업은 실패하지 않았다.

## 배포 보존과 한계

9개 서비스 실행, 명시적 상태 검사5개 healthy다. worker·dispatcher·monitor만 교체했다. 나머지 컨테이너 ID, 볼륨, 비공개 환경 파일, 기존 서버 결과물4개와 로컬 검수 파일/ZIP 해시를 보존했다. DB 아카이브119항목·영상84객체의 백업과 롤백 이미지 태그가 있다. 실제 제공 영상의 최신 검수본 `2714865c`와 미승인 상태도 유지한다.

비공개 근거는 `recording4-local-tools/experiments/multicut-timing-{before,backup,after}-20261001.json`, 진단용 `multicut-timing-20261001/`, 운영 표본 `multicut-timing-smoke-20261001/`의 요청·작업·수집 파일·`report.json`·`visual-review.json`이다. 원시 영상/음성/자막/프레임은 커밋하지 않는다.

이는 편집 시간축과 운영 경로의 검증이다. 사람 음질 청취, 실제 영상 전체의 자막/모자이크 검수, 화자·번역 정확도 향상을 입증하지 않는다. 실제 검수본의 사람 검수와 게시 승인은 남아 있다. main CI와 최신 운영 상태는 [HANDOFF](../../HANDOFF.md)를 따른다.
